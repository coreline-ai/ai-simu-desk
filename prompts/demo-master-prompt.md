# 전문가 검토·개발 계획·생성 에셋·1차 데모 통합 프롬프트

아래 블록을 프로젝트 루트에서 작업하는 코딩 에이전트에게 전달한다. 기존 문서와 데모가 있으면 먼저 읽고 이어서 작업한다. 이미지 생성 기능이 없는 환경에서는 생성했다고 표시하지 말고 제약을 보고한다.

```text
너는 제품 엔지니어링 리드이자 인터랙티브 비주얼 디자이너다. AI 동료가 있는 작은 오피스의 1차 시각 데모를 완성하라. 설명과 계획에서 멈추지 말고 실제 이미지 생성, 프로젝트 저장, 동적 에셋 연결, 로컬 실행, 브라우저 검증, 결과 표시까지 수행하라.

[근거와 목표]
- 참고 URL은 https://deskrpg.com/auth 이다. 앞선 조사에서는 Coming Soon이었다. 필요하면 현재 공개 화면과 공식 저장소를 확인하라. 인증 후 기능을 직접 검증했다고 주장하지 말라.
- 핵심 경험은 직원 선택 → 업무 요청 → 진행 → 승인/취소 → 결과 확인이다.
- 임시 제품명은 AI Simu Desk, 사무실 하나, 직원 둘(나라: 기획·리서치 / 준: 개발·설계)이다.
- 이번 결과는 생성 PNG와 프레임 애니메이션을 합성한 2.5D 모의 데모다. 실제 AI·실시간 3D라고 표시하지 말라.

[1. 전문가 검토]
AGENTS.md, README.md, docs와 기존 개발 계획을 먼저 읽고 사용자 변경을 보존하라. 사실/가정/제안을 구분하라. 구조, 데이터 소유권, 실패·취소·승인·중복 명령, 접근성, 에셋 일관성, 성능, 검증 가능성을 검토하라. docs/expert-review.md에 ready / needs revision / blocked 판정과 우선순위별 위험·수정안을 기록하라. 파일 길이를 곧바로 결함으로 단정하지 말라.
원본 코드·로고·에셋을 복사하지 말라. 이미 원본 소스를 열람했다면 엄격한 클린룸 개발이라고 주장하지 말라. 재사용 시 원본과 제3자 라이선스를 먼저 확인하라.

[2. 개발 계획]
dev-plan/implement_YYYYMMDD_HHMMSS.md를 만들라. 같은 작업의 기존 계획이면 이어서 갱신하라. 개발 목적, 개발 범위, 제외 범위, 참조 문서, 공통 규칙, Phase 상태, QA 관점을 포함하라. 각 Phase에 구현 체크박스, 자체 테스트, 이슈·수정, 완료 조건을 넣어라. 자체 테스트를 마친 후 다음 Phase로 진행하고 실제 완료만 체크하라.
순서는 검토·계약 → 에셋 생성·채택 → 데모 구현 → 검증·인계다. 실제 AI, Hermes, DB, 로그인, 결제, 다중 사용자, 회의, 예약 실행, 공개 배포는 제외하라.

[3. 실제 이미지와 동적 에셋]
내장 이미지 생성 도구로 prompts/assets/office-background.txt의 배경과 coworkers-atlas-v2.txt의 투명 아틀라스를 각각 생성하라. 기존 실제 에셋이 충분하면 보존·재사용하라. 현재 선택된 직원 에셋은 coworkers-atlas-v2.png이며 v1은 과거 원본이다.
배경은 아이보리·세이지·옅은 오크·테라코타의 자체 미니어처 오피스다. 두 워크스테이션을 합성할 전면 바닥을 비워라. 글자·로고·UI·인물은 넣지 말라.
아틀라스는 동일 카메라·고정 앵커의 4열×4행이다. 0행 나라 휴식, 1행 나라 타이핑, 2행 준 휴식, 3행 준 타이핑, 각 행 네 프레임이다. 배경을 스타일·광원·카메라 참고로 지정하고 true alpha transparency를 요청하라.

생성 결과가 정확한 균등 픽셀 그리드라고 가정하지 말라. 발·의자·책상이 잘리지 않는 원본 영역을 실측하고 scene-frames.mjs에 기록하라. 같은 바닥 기준점으로 종횡비를 유지해 렌더링하라. 책상 전면 방향, 배경 가구와의 상대 크기, 창 쪽 광원과 접지 그림자를 실제 합성 화면에서 비교하라. 전체 실루엣 drop-shadow로 접지 그림자를 대체하지 말라. 현재 v2 배치와 검증 기준은 docs/visual-calibration-review.md와 docs/demo-spec.md를 따른다. 화면 크기 1280/768/390/319px와 모든 16프레임의 바닥 지지 영역을 재검증하라.
도형·이모지·핫링크로 실제 생성 에셋을 대체해 완료하지 말라. 결과를 직접 보고 실제 크기, 알파, 그리드와 프레임 앵커를 검증하라. 요청 크기와 반환 크기가 같다고 가정하지 말라.
최종 파일을 demo/assets/에 저장하라. 기본 생성 폴더에만 의존하지 말라. manifest.json에 실제 파일·크기·프레임·행 의미·출처·제약·프롬프트를 기록하라. PNG를 GLB·리깅 모델이라고 표시하지 말라.

[4. 구현 계약]
작은 로컬 데모는 외부 의존성 없는 HTML/CSS/ES modules로 구현하라. 기존 프로젝트는 기존 도구를 우선 사용하라.
- domain.mjs: 순수 상태·입력 검증. DOM·타이머·네트워크 의존 금지.
- app.mjs: UI 이벤트와 모의 타이머. 상태 변경은 domain을 통해서만 수행.
- scene.mjs: 아틀라스 프레임·화면 표현·수명. 업무 실행 변경·AI 호출 금지.
한 번에 실행 하나, 입력은 공백 제거 후 2~400자다. 텍스트는 textContent로 표시하라. queued → running → succeeded | failed | cancelled, running → awaiting_approval → running을 정의하라.
실행 ID, 중복 방지 키, 예상 단계를 사용하라. 중복 명령, 다른 실행 콜백, 중복 단계와 종료 후 콜백은 무시하라. 정상 완료·승인 대기·연결 실패의 모의 시나리오, 취소, 승인/거절, 새 ID를 사용하는 재시도를 제공하라.
결과는 직원별 고정 예시이며 실제 AI 추론이 아님을 표시하라. 외부로 입력을 전송하지 말라. 기록은 현재 탭 메모리 최대 10개다. 새로고침 시 초기화를 표시하라.

[5. 화면]
읽기 좋은 한국어, 시스템 글꼴, 불투명한 패널, 명확한 버튼과 집중된 업무 흐름을 구성하라. 실제 배경 위에 두 움직이는 워크스테이션을 합성하고 UI 글자는 HTML로 표시하라. 직원은 씬·명단에서 선택할 수 있어야 한다. 에셋 보기에서 원본 PNG와 두 동작을 확인하게 하라.
390px에서는 세로 배치와 44px 터치 영역을 제공하라. 가로 스크롤·잘림·겹침을 수정하라. prefers-reduced-motion, 수동 움직임 정지, 비활성 탭 정지를 지원하라. 시각 움직임 정지와 업무 타이머를 분리하라. 레이블, 키보드 포커스, 상태 텍스트, 이미지 실패 대체 표현과 모달 Escape 닫기를 제공하라.

[6. 검증·보고]
정상 완료, 승인 전 진행 차단, 취소 후 늦은 완료 차단, 중복 요청·단계 방지, 입력 경계, 실패 재시도 테스트를 실행하라. JS 구문 검사와 실제 데스크톱·모바일 브라우저 QA를 수행하라. 이미지 로딩, 실제 프레임 변경, 직원 선택, 승인·실패·취소·재시도, 움직임 정지와 기록을 확인하라.
화면 증거와 QA 결과를 남기고 계획을 갱신하라. 실측하지 않은 FPS·LCP를 통과했다고 표시하지 말라. 최종 답변에는 실제 화면 또는 동작 미리보기, 개발 계획·통합 프롬프트·에셋 경로, 실행 명령과 제약을 짧게 제공하라.
이미지 도구나 브라우저가 실패하면 실패를 알리고 가능한 검증을 이어가라. 자동으로 유료 외부 API나 다른 모델로 바꾸지 말라.
```
