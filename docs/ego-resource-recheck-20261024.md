# Ego Lite 실제 자원·접촉 재검수 · 2026-10-24

## 결론

- **표본 품질 유지:** 35개 동일 시점/시점 방향의 framebuffer 해시·전체 런타임 진단·손 접촉 결과가 이전 버전과 일치했다. 기존 어색한 조형까지 개선됐다는 뜻은 아니다.
- **업무 CPU 작업량 감소:** 동일한 브라우저 WebGL 작업에서 CPU 시간 중앙값 494.331 → 413.021ms, 약 **16.45% 감소**. 3회 짝 비교 모두 감소했다.
- **대기 CPU·RAM은 절감 확정 불가:** 대기 결과는 순서별로 엇갈렸다. 유지 JS 힙은 약32MiB로 비슷하고 RSS는 일부 조건에서 증가했다. 메모리 최적화 성공으로 표시하지 않는다.
- 일반 Google Chrome은 WebGL 오류가 남아 있으며 전체 재시작은 하지 않았다. 사용자의 선택에 따라 Ego Lite에서 검수했다. 보안 보호·제품 FPS/DPR/시각 품질 설정을 낮추지 않았다.

## 비교 조건과 측정 정의

기준 `b963d17` / 최적화 `14e7c9e`. 같은 v9 GLB·전원 손 v14, Apple M4 / ANGLE Metal, Ego Lite Chromium154, balanced, DPR1.5, CSS1100×740 / framebuffer1650×1110. 공개 in-memory fixture만 사용했고 사용자 DB·설정·실행 release를 수정하지 않았다. Git 소스 지문은 이전 검수와 동일하다.

CPU는 CDP `Performance.getMetrics.ProcessTime` 누적값의 차이다. Chromium 구현은 현재 **렌더러 프로세스의 누적 OS CPU 시간**을 읽는다([공식 소스](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/inspector/inspector_performance_agent.cc)). GPU·브라우저 본체·서버·다른 렌더러를 포함한 전체 앱 사용량이 아니다. 점유율 표시는 CPU 시간/경과시간이며 한 코어100% 기준이다.

RSS는 `ps`의 동일 렌더러 resident set으로 공유 페이지도 포함한다. JS 힙은 GPU 버퍼/텍스처·전체 물리 메모리가 아니다. PID는 별도 짧은 CPU 교정과 누적 시간 일치로 식별했으며 교정은 측정 구간에서 제외했다.

## 1. 실제 자동 재생 관찰

대기·5명 업무 variant1·화면 밖 각3회, 이전/최적화 순서를 교차해 총18개 구간을 측정했다. 각 구간은 최소6초다. 자동화 RAF가 약0.98~2.57Hz로 달랐고 시각 시뮬레이션 진행량도 달랐다. 따라서 아래는 **그 환경의 실제 관찰값이지 개선율을 계산할 동등 처리량 비교가 아니다**. 정상 전경 FPS/CPU/전력 수치로 일반화하지 않는다.

| 상태 | CPU 중앙값 이전 → 최적화 | JS 힙 중앙값 이전 → 최적화 | RSS 중앙값 이전 → 최적화 |
|---|---:|---:|---:|
| 대기 | 9.97% → 11.00% | 47.97 → 48.11MiB | 204.16 → 201.77MiB |
| 역할 업무 | 14.74% → 10.94% | 44.12 → 43.84MiB | 247.94 → 186.34MiB |
| 화면 밖 | 9.32% → 5.64% | 53.12 → 44.63MiB | 295.09 → 284.02MiB |

화면 밖 최적화본은 3회 모두 render 제출0, 시뮬레이션은 계속 진행했다. 마지막 표본의 진행량 차이도 원시 데이터에 보존했다. 단순히 CPU가 낮다는 이유로 같은 효과를 더 저렴하게 냈다고 판정하지 않는다. 처음 실행한 비동등 RAF 표본과 복구 탐색 표본은 성공 집계에서 제외했다.

## 2. 같은 작업량의 실제 WebGL 비교

RAF 차이를 제거하기 위해 **60 fixed steps + 15회 명시적 그리기 + 검사용 readback 직전1회 그리기(총16회)**를 같은 장면에서 수행했다. readback 비용은 양쪽 모두 포함했다. 생성/셰이더 준비·GC는 CPU 시간에서 제외했다. 각 조건3회 순서 교차, 총12개 완료 표본이다. 이는 브라우저에서 실제 렌더한 통제 워크로드이며 일반 자동 재생 FPS나 전체 앱 점유율이 아니다.

| 조건 | 이전 CPU 중앙값 | 최적화 CPU 중앙값 | 해석 |
|---|---:|---:|---|
| 대기 | 374.225ms | 330.235ms | 중앙값은 -11.75%지만 짝 비교3회 중2회 증가. 안정적 개선으로 판정하지 않음 |
| 5명 역할 업무 variant1 | 494.331ms | 413.021ms | 중앙값 -16.45%, 짝 비교 모두 감소(16.45% / 16.17% / 35.35%) |

각 조건의 최종 framebuffer·전체 런타임 해시도 동일했다. 3표본의 방향 확인이지 통계적 성능 보장/목표 자원 상한이 아니다. 다른 앱은 종료하지 않았다.

## 3. 캐릭터·손·소품

기본26개 + 보강 포즈3개 + 반대 시점 컵5개/실제 키 누름1개 = **35/35 쌍 일치**. 대기, 전체 업무2/4/8초, 5명×업무3변형 손 확대, 전원 컵, 준 안경, 문서 전달을 비교했다. 새 손 누락·변형 차이·접촉 소유권 차이는 표본에서 발견하지 않았다. 나라/소라 필기, 준 입력·마우스, 민 체크, 레오 문서의 서로 다른 포즈를 실제 캡처로 확인했다.

처음 마우스5초/안경4초는 이미 손을 회수한 구간이었고, 키2.3초도 press 이벤트가 없는 표본이었다. 이를 접촉 검수로 간주하지 않고 다음 실제 접촉 구간을 추가했다.

- 준 마우스2.5초: `mouse-contact`, 실제 `JunMouseShell` raycast 대상4개, 목표 대비 최대 오차 약0.455mm. 기존4mm 패드 여유 계약 유지.
- 준 실제 키 누름2.35초: 왼손 press 이벤트 발생, 오차 약0.630mm. 이벤트 없는 프레임을 키 접촉 통과로 집계하지 않았다.
- 준 안경1.5초: adjust0.35초, 기존 검지/테 접촉, 최종 world pad 오차1mm 미만. 이전/최적화 동일.
- 전원 컵: 기존 legacy 소유 접촉과 손 소유권 유지, 반대 카메라에서도 전후 결과 동일. 팔·얼굴에 컵이 가려지는 기존 구간이 있어 소라의 메시/부모 visible 상태와 전원의 소유권·접촉 수치도 확인했다. 모든 각도의 완전한 시각적 접촉을 보장하지 않는다.

손 크기·소매 경계, 컵/문서의 단순 주먹형 그립 등 이전에 수용한 스타일 한계는 그대로다. 모든 피부 폴리곤의 무관통이나 모든 프레임의 자연스러움을 새로 입증한 검사가 아니다.
