# 손 자연스러움 · 다섯 동료 개성 강화 제안

- 작성일: 2026-10-24, Asia/Seoul
- 상태: 읽기 전용 코드 분석 및 5명 캐릭터별 전문 검토를 종합한 **제안**. 캐릭터 구현은 착수하지 않았다.
- 방향: 공용 손·접촉 계약을 먼저 검증한 뒤, 캐릭터별 5개 전담 작업으로 분리한다.
- 이번 분석은 동시 실행 한도에 맞춰 3명 + 2명으로 나누어 수행했다. 5개 담당을 같은 순간에 실행했다고 표시하지 않는다.

| 자동 검수는 통과하지만 개성은 약함 | 기존 검사는 접촉·예약·소유권·중단/복귀 등 기능 계약 중심이다. | 수치 통과를 자연스러움·인물 식별성의 증명으로 사용하지 않는다. |

## 2. Blender가 필요한가

**실시간 Blender 연결은 필수가 아니다.** 현재 코드만으로도 손가락 비율·굴곡·소품별 그립·타이밍과 개별 행동을 개선할 수 있다.

다만 손 근접 화면의 완성도까지 높이려면, 공통 손을 연속된 스키닝 메시로 만드는 방향을 권장한다. Blender는 이 메시의 모델링·웨이트·손가락 리그·보조 포즈를 제작하고 검수하는 도구로 사용할 수 있다. 결과를 GLB로 내보내고 Three.js에서 로드하면 되므로 서비스 실행 중 Blender를 켜 둘 필요는 없다.

권장 경로는 **Blender로 공통 손 에셋 제작 → GLB → 기존 손목/소품 접촉 솔버와 결합**이다. 전신·사무실·기존 모션을 한꺼번에 교체하지 않는다. 절차적 손 스키닝을 코드로 제작하는 대안도 가능하지만, 어느 도구든 손 모델·웨이트·포즈의 시각 검수가 필요하다. 저장소에서 기존 `.blend` 원본은 발견되지 않았다.

공식 근거:
- [Khronos Blender glTF importer/exporter](https://github.com/KhronosGroup/glTF-Blender-IO)
- [Three.js animation system](https://threejs.org/manual/pages/animation-system.html)
- [Three.js SkinnedMesh](https://threejs.org/docs/pages/SkinnedMesh.html)

## 3. 공통 선행 작업 — 리드 단독 소유

### 손 형태
- 손바닥과 손가락이 이어지는 피부 메시, 관절에서 찌그러지지 않는 웨이트를 만든다.
- 검지·중지·약지·소지의 길이·굵기·벌어짐을 구분하고, 엄지의 손바닥 맞은편 회전을 별도로 설계한다.
- 긴 손가락의 세 관절 움직임을 표현하되, 관절 수를 늘리는 것만으로 자연스러워졌다고 판단하지 않는다.
- 원경·근접의 품질 단계를 나누고, 손톱·관절 구체가 초기 프레임에 큰 도형으로 노출되는 이전 결함을 회귀 검사한다.

### 손 행동
- 필기 삼점 집기 / 컵 손잡이 / 반대 손 컵 지지 / 종이 집기 / 마우스 / 타이핑 / 휴식 손을 구분한다.
- 손목 도착 뒤 손가락이 순차적으로 접촉하고, 놓을 때는 접촉을 풀고 손목을 회수하도록 설계한다.
- 손가락별 작은 시간차·굴곡 차이는 넣되 떨림이나 의미 없는 상시 움직임은 피한다.
- 손가락을 늘리거나 접촉 목표를 빈 공간으로 옮겨 검사 수치를 맞추지 않는다.

### 공통 계약과 소유 경계
- 리드만 공용 손 솔버, 런타임 적용 순서, 공유 스케줄러, 빌드/GLB 통합을 수정한다.
- 캐릭터 담당은 자신에게 할당된 모듈에서 행동 의도·손 포즈·시선·표정·소품 접촉 타깃만 작성한다.
- 손목·발 접지·소품 소유권·업무 선점·복귀의 최종 권한은 기존 공용 시스템이 유지한다.
- 새 프로필은 공통 시뮬레이션 시간을 사용한다. 독립 타이머나 비결정적 난수를 추가하지 않는다.
- 개인 동작의 시작 위상·지속·멈춤을 다르게 하되, 서버 업무·승인·저장 시간은 바꾸지 않는다.
- 새 손 리그가 공동 관찰의 노드 목록/스키마에 영향을 주는지 확인한다. 기존 패킷을 그대로 호환한다고 가정하지 않는다.

공통 수정 후보: `pilot-3d/activities/hand-grips.mjs`, `pilot-3d/ensemble-office/hand-surface.mjs`, `pilot-3d/activities/desk-actions.mjs`, `pilot-3d/activities/team-runtime.mjs`, `pilot-3d/personal-office/recipes.mjs` 및 필요한 모델/빌드 통합 코드.

## 4. 캐릭터별 5개 전담 작업

아래 경로는 **신규 경로 제안**이며 아직 생성하지 않았다. 각 담당은 자기 디렉터리와 자기 테스트만 수정한다. 공유 계약은 공통 선행 단계에서 확정한다.

| B · 소라 / 디자인 | 시각적으로 탐색하고 보여 주는 사람 | 큰 곡선 스케치 후 구도 확인 / 색상 견본 대조 후 수정 / 태블릿을 동료 쪽으로 돌려 설명 | 필기 손과 지지 손 분리, 펜 끝→견본→동료 시선, 넓은 곡선과 열린 어깨 | `pilot-3d/character-personalities/sora/`, `product/tests/personality-sora.test.mjs` |

모든 담당의 산출물:
- 대표 업무 동작 3개, 휴식 습관 1개, 완료 반응 1개.
- 개인별 프로필·동작·필요 소품 정의와 독립 테스트.
- 같은 카메라/배속/조명에서의 전후 영상, 손 근접·측면 캡처.
- 작업 취소·업무 선점·일시정지·소품 반납 검증 결과.

같은 필기를 속도와 색만 바꾸거나, 안경·끄덕임을 과도하게 반복시키는 결과는 개성 강화 완료로 인정하지 않는다.

## 5. 진행·통합 순서

1. **기준 고정:** 현재 로컬의 캐릭터 표시·자동 재생 수정과 테스트를 보존한다. 실행 전 기준 스냅샷/승인된 커밋을 정하고, 작업자별 독립 작업 공간을 만든다. 무단 stash/reset/커밋을 하지 않는다.
2. **공용 손 선행:** 손 한 쌍을 기준 캐릭터에서 검증한다. 펜·컵·종이·키보드·마우스와 근접 변형을 확인하고 시각 방향을 승인받는다.
3. **공유 계약 동결:** 캐릭터가 출력하는 동작/그립/시선/표정 의도, 적용 순서, 이름·단위·기준 자세·소유권을 확정한다.
4. **5개 캐릭터 작업:** 공통 기준을 각 전담에 전달한다. 공용 파일 수정이 필요하면 직접 수정하지 않고 리드에게 요청한다. 현재 실행 한도에서는 3개 + 2개 묶음으로 운영한다.
5. **직렬 통합:** 각 전담의 범위 검사·독립 검수를 통과한 뒤 한 명씩 연결한다. 필요하면 실제 비교를 위한 새 버전을 두고 현재 버전을 복구 경로로 보존한다.
6. **5인 연출 검수:** 첫 20초 안에 각자의 대표 동작을 노출하고, 업무 시작·멈춤·시선·휴식을 엇갈리게 배치한다. 모든 인물이 동시에 같은 펜 동작을 시작하는 기존 인상을 없앤다.

병렬화의 이득은 캐릭터별 연출·소품·테스트가 독립적이라는 점이다. 공용 손 리그나 동일 스케줄러를 5명이 동시에 설계하면 충돌과 재작업이 커지므로 그 부분은 병렬화하지 않는다.

## 6. 완료 판정

아래는 앞으로 수행할 **합격 기준**이며 아직 달성 결과가 아니다.

- 이름표와 색상 단서 없이도 업무 동작으로 다섯 명을 구별할 수 있는지 사용자/독립 검수자가 평가한다.
- 기본 카메라에서도 차이가 보이고, 손 근접·측면에서는 손가락 연결·엄지 집기·손톱 방향·접촉/해제가 자연스러워야 한다.
- 기존 유효 접촉 검사와 실제 표면 검사를 유지한다. 수치 통과만으로 전체 피부 비관통·모든 프레임의 자연스러움을 보장하지 않는다.
- 자동 재생·새로고침·수동 정지/재생·업무 선점·취소/복귀·공동 관찰·구형 복구 경로를 회귀 검사한다.
- 개인 동작 15종과 5인 동시 재생을 녹화해 검수한다. 대표 구간에서만 정상인 결과를 피하기 위해 전환 구간도 포함한다.
- 같은 장치·브라우저·카메라에서 프레임 시간·draw call·JS heap·반복 생성/해제를 기준판과 비교한다. 성능 예산은 손 선행 샘플 측정 후 확정한다.
- 변경된 계약의 자동 검사, 타입/경계/문법 검사, 전체 회귀 및 실제 브라우저 검수를 별도로 기록한다.

## 7. 권장 선택

**공통 손 리그 보강 + 캐릭터별 행동 연출 5개 전담**을 권장한다. Blender 실시간 연결부터 구성하거나 사무실·전신을 모두 갈아엎는 작업은 선행 조건으로 두지 않는다. 필요하면 공통 손 에셋만 Blender에서 제작해 기존 런타임과 결합한다.

기존 로컬 수정은 이번 제안에서 바꾸지 않았으며, 테스트·빌드·실제 구현을 새로 실행한 것으로 보고하지 않는다.
