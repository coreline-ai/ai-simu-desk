## 확인한 P1 · 우선 보정

### S-01. 협업 Fake AI의 제외 조건 우회

- 근거: [fake-answer.ts](../server/domain/fake-answer.ts) 179~185행은 금지 작업이 있으면 `body`만 보류 문구로 바꾼다. 199~206행의 팀 합성은 남아 있는 `items`와 첫 항목 요약을 다시 공개한다.
- 재현: `로그인 제외. 개발 계획을 작성해줘`는 단독 결과에서 보류되지만 `team:true` 결과에 `이메일 로그인` 작업이 포함된다. 독립 재실행에서 `soloBlocked=true`, `teamExcludedTask=true`.
- 영향: 화면 결과와 인계 요약이 명시한 조건을 위반한다. 외부 AI 호출 문제는 아니다.
- 최소 보정: 결과의 확정/보류 상태를 명시하고 본문·항목·인계 요약이 같은 판정을 사용하게 한다. 새 생성 버전을 기록하되 이미 저장된 답변과 재시도 스냅샷은 보존한다.
- 회귀: 단독/5역할/수정/수동 인계/재시도, 제외·충돌·문자 그대로 허용된 조건을 함께 검사한다. 사용자 요청을 그대로 표시한 문장과 실제 추천 작업을 구별한다.

### S-02. 게스트 소유 공동 공간의 만료 후 고착

- 근거: [workspace-store.ts](../server/db/workspace-store.ts) 42~50행은 게스트의 소유 공간 생성을 허용한다. [guest-auth.ts](../server/adapters/guest-auth.ts) 27~29행은 새 ID/고정 2시간 세션을 사용한다. [studio-store.ts](../server/db/studio-store.ts) 33~37·48~49행은 소유자 제어와 활성 실행 하나를 보장하지만 소유자가 사라진 경우의 종료 경로가 없다.
- 재현: 게스트 owner가 승인 대기 업무를 만든 뒤 해당 세션을 만료시킨다. owner `/api/me` 401, 남은 일반 member 조회 가능, 취소 403, 새 업무 409, 실행은 `awaiting_approval` 유지.
- 영향: 로그아웃/만료 후 복구할 수 없는 게스트 소유자가 남고 공간의 새 업무가 막힐 수 있다. 탭 종료는 세션 만료와 같지 않으므로 두 경우를 분리해야 한다.
- 최소 보정: **게스트 소유 공간의 수명 정책을 먼저 확정**한다. 추천은 영속 공동 공간의 owner를 일반 계정으로 제한하고 게스트의 참여 권한은 유지하는 것이다. 기존 게스트 소유 공간은 자동 삭제하거나 임의의 참여자를 owner로 승격하지 않는다. 백업 후 명시적 인계/체험 종료와 대기 업무 정리 절차가 필요하다.
- 회귀: 기존 공간 보존, 만료/로그아웃/탭 종료의 구분, 정회원 owner의 일시 부재, 다른 계정의 소유권 탈취 방지, 5명 게스트 협업을 검사한다. 이 정책은 이번 문서의 제안이며 아직 적용하지 않았다.

### S-03. 백업이 원본 DB를 먼저 마이그레이션

- 근거: [backup-db.ts](../scripts/backup-db.ts) 10~14행은 [database.ts](../server/db/database.ts) 34~40행의 자동 migration 연결을 연 뒤 덤프한다.
- 재현: 임시 구스키마 DB의 적용 migration이 백업 연결 전 2개에서 덤프 직전 11개로 바뀐다.
- 영향: 업데이트 **전** 상태를 확보하는 안전장치로 사용할 수 없다. 현 migration에서 실제 데이터 손상이 발견됐다는 뜻은 아니다.
- 최소 보정: 연결·잠금과 migration 실행을 분리한다. 백업은 원본 스키마를 변경하지 않고, 복구도 원본 아카이브를 보존한 새 경로에서 검증/업그레이드한다.
- 회귀: 스키마 목록·업무/계정 데이터 지문이 백업 전후 동일, 새 migration이 실패해도 구버전 백업 생성 가능, 사용 중 DB 거절, 잘못된 아카이브/기존 대상 덮어쓰기 거절.

### S-04. 방문 중 완료·인계 동작 유실

- 근거: [expressive-scheduler.mjs](../pilot-3d/activities/expressive-scheduler.mjs) 11·28행의 cue 보관/재생은 `records`와 역할 소품만 본다. [interaction-scheduler.mjs](../pilot-3d/activities/interaction-scheduler.mjs) 43·61행의 v6 방문은 별도 `visit`에서 표시를 점유한다.
- 재현: 나라가 방문 출발 `out` 중 `success`/`sending`/`receiving` 각각을 0.025초 받은 뒤 idle로 돌아오면, 복귀 후까지 `pendingAfterCue=0`, `cueEverShown=false`.
- 영향: 업무 저장·완료 시각은 유지되지만 완료/인계가 시각적으로 누락된다.
- 최소 보정: 방문/문서가 포함된 표시 점유 조건을 cue 보관과 재생 양쪽에서 사용한다. 새 실제 업무·공간 폐기는 이전 cue보다 우선한다.
- 회귀: 양쪽 인물, 방문 출발/도착/문서 수신/복귀, 완료/오류/송수신, 일시정지·상대 제거·새 업무·중복 cue를 검사한다.

## 계획 검토와 통합 순서

1. **백업을 먼저 안전하게 만든다.** 소유권/DB 정책 변경 전에 되돌릴 원본을 확보한다.
2. 소유권 수명과 AI 결과 확정 계약을 정한 뒤 각 최소 수정에 실패 재현→수정 후 통과 검사를 붙인다.
3. 동작 점유와 UI 요청 순서를 보정한다. 실제 업무 계약과 시각적 소품 인계는 계속 분리한다.
4. 자동 합격 조건을 강화하고 관측/실제 기기·동시 사용을 검사한다.
5. 마지막으로 산출물 교체·문서/허브·이전 데모 회귀를 묶어 로컬 안정화 후보를 확정한다.

불필요한 공통 프레임워크, 전면 타입 전환, 새 외부 DB/AI/배포, 더 많은 동작 추가는 이번 계획에서 제외한다. 구현과 커밋·푸시는 이번 요청에서 수행하지 않았다.
